Overview

SupportOS brings technical support workflows into one web workspace. The repository contains an active MVP foundation, with ongoing stabilization and testing.

Problem

Engineers switch between vendor documentation, internal notes, terminals, vulnerability feeds, and case records. Useful investigation context is difficult to carry between these tools.

Constraints

Private knowledge must respect user visibility. Credentials must stay outside AI context. SSH must work independently of AI availability.

Architecture

A Next.js web interface connects to a Python FastAPI service. PostgreSQL and pgvector support records and knowledge retrieval; Redis supports shared runtime services. Docker Compose brings the services together, with optional local inference through Ollama.

What I built

The repository includes authentication and role-based access, private chat, scoped knowledge ingestion and retrieval, WebSocket SSH terminals, a floating workstation shell, assets, cases, runbooks, evidence analysis, and vulnerability intelligence.

Technical decisions

SupportOS keeps remote operations, knowledge retrieval, and AI assistance as separate capabilities so critical support workflows do not depend on a model being available. Access boundaries and credential handling remain explicit parts of the architecture.

Challenges

The engineering work includes cross-user isolation, host-key verification, provider failures, retrieval quality, and reliable integration between the frontend and API.

Results

A working application foundation now connects these workflows. This is an active development project; no production adoption, time-saving percentage, or reliability metric is claimed.

Technology

Next.js · React · FastAPI · PostgreSQL · pgvector · Redis · AsyncSSH · Ollama · Docker

What I learned

Connecting tools is only part of the work. Access boundaries, evidence handling, and recoverable failures need to remain consistent across the workspace.
